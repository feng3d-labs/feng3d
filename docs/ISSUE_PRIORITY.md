# Issue 优先级标准

> 状态：**现行规范**。四档标签的判据、定级流程与维护机制。

## 为什么需要这份文档

2026-09 对全部开放 issue 做过一次优先级定级，四档标签是：

`优先级-阻塞` · `优先级-高` · `优先级-中` · `优先级-低`

但**标签本身不会自我维持**——半年后 `优先级-高` 里躺着三十个 issue 时，这套体系就失效了。所以判据必须成文，且**有一个机器执行者**（见 §5，对齐仓规 [§15](../AGENTS.md) 的元规则：每条规范必须有执行者）。

## 1. 四档判据

| 档 | 判据 | 典型信号 |
|---|---|---|
| 🔴 `优先级-阻塞` | 不做完，其它工作**无法开始**或**无法验收** | 它是别人的前置；没有它，后续任务连"做对了没有"都判不了 |
| 🟠 `优先级-高` | ① **数据正确性 bug / 安全 / 崩溃**；② [POSITIONING.md](./POSITIONING.md) §6 已排序的发展优先级（错误可观测性 → TSL 收回 → 编辑器收回 → 门禁体系）；③ **editor v2 核心路径** | 用户能观察到"结果是错的"；或战略排序里明确排在前面的 |
| 🟡 `优先级-中` | 游戏项目的**基本需求**、体验与性能改进、有明确需求但不阻塞 | "该有"，不挡路 |
| 🟢 `优先级-低` | **技术储备 / 预研**、长期展望、POSITIONING 明确列为**非目标**的、**工程卫生** | "将来可能"，或纯粹让仓库更整洁 |

## 2. 定级流程（三步，不要跳）

1. **它挡住别人了吗？** 有人因为等它而无法开始或无法验收 → 🔴 阻塞。**不是"很重要"就算阻塞**，只有"卡住别人"才算。
2. **它会让用户看到错误结果吗？** 数据算错、崩溃、安全问题 → 🟠 高。其次看它在 [POSITIONING.md](./POSITIONING.md) §6 的战略排序里排第几、是不是 editor v2 的核心路径。
3. **排除法是"中"还是"低"？** 是"游戏项目该有的能力、有明确需求" → 🟡 中；是"预研 / 长期 / 非目标 / 工程卫生" → 🟢 低。

### 特别提醒：**别让优先级通胀**

- **"很重要" ≠ 阻塞。** 阻塞的定义是"卡住别人"，它是个**依赖关系**判断，不是"重视程度"判断。一个又大又难、但没人在等它的功能，是**中**或**低**，不是阻塞；
- **"我想做" ≠ 高。** 高的一档里有硬判据（正确性 / 安全 / 崩溃 / 战略排序 / editor v2 核心路径），拿不出其中任何一条就不该进高；
- **正文为空、没有验收判据的 issue 不应该进"高"。** 连"怎么算做完"都不知道的东西，定成高只会把真正紧急的事挤下去——这类 issue 应当**先补需求**（见 §6）。

## 4. 标签名必须与 GitHub 上完全一致

仓库里**实际存在**的优先级标签只有这四个（实测仓库共 33 个标签）：

```
优先级-阻塞
优先级-高
优先级-中
优先级-低
```

**新增档次必须先在这份文档里加判据**，再去 GitHub 建标签——不要反过来（先建标签、再补文档），那会让"判据"落后于"实际标签"，体系就失去依据了。

## 5. 机器执行者

| 机制 | 位置 | 做什么 |
|---|---|---|
| 漏标检测 | `scripts/check-issue-priority.mjs` | 列出全部开放 issue，**任何一条没有 `优先级-*` 标签、或带多于一个优先级标签，都以非零码退出**并逐条列出 |
| 离线自检 | `test/IssuePriority.spec.ts` | 用固定的 issue 数据（含"无标签"「多标签」样例）断言判定结果，不需要网络与凭据 |

拉取真实数据需要 GitHub 凭据（脚本用 `gh api`，或 `--from <file>` 从本地 JSON 读，便于离线调试与测试）。

## 6. 维护规则

- **新建 issue 时必须同时定级**——按 §2 的三步走，选一个恰好一个优先级标签；
- **正文为空 / 没有验收判据的 issue**：先补需求再定级，或明确关闭/冻结。仓库里有一批历史遗留（Gitee 迁移）属于此类；
- **复核时机**：每次发版前过一遍「阻塞」与「高」两档（见 [CI.md](./CI.md) 的发布检查清单）——低档的过期项危害有限，这两档躺着过期项会误导排期；
- 复核时顺手处理**明显过期**的（已完成、重复、已成非目标）→ 关闭或改档，而不是留着。
