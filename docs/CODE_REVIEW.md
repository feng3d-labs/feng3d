# 代码审查标准

> 状态：**现行规范**。补根 [AGENTS.md](../AGENTS.md) §15 元规则主动放弃的那一块——**注定写不成脚本的判断**。

## 为什么需要这份文档

根 [AGENTS.md](../AGENTS.md) §15 的元规则是「每条规范必须有机器执行者，无执行者的只能写进建议，不算规范」。
这条规则把 42 个门禁脚本、eslint（含 `feng3d/*` 自研规则）、`tsc`、覆盖率门禁能查的东西全管住了，
但**留下一块空白**：「模块够不够深」「这个抽象放得对不对」「diff 是否忠实实现了 issue 的意图」——
这些**注定写不成脚本**。

空白不该等于「没人负责」。这份文档登记这一块，由 **review 承担**，判据是人的判断 + 下面的坏味道清单。

## 1. 两轴分开报告

对照 `git diff <定点>...HEAD`（三点，比对 merge-base）逐条过两轴，**分成两份报告，不合并、不重排**：

| 轴 | 问题 | 依据 |
|---|---|---|
| **规范轴** | diff 是否违反本仓**已文档化**的规范？ | 根 [AGENTS.md](../AGENTS.md)、子包 `AGENTS.md`、`docs/**` 里写明的规则 |
| **规格轴** | diff 是否**忠实实现**了它声称要解决的问题？ | 对应 issue 正文 / 计划 / `docs/` 里的设计文档 |

两轴可以**一过一败**：全部合规但做错了事（规范 pass / 规格 fail）；完全照 issue 做但破坏了约定（规格 pass / 规范 fail）。
分开报告正是防止一轴掩盖另一轴。结尾给**每轴各自的发现数**与**各轴最严重的一条**——
**不要**跨轴挑一个总冠军，那正是两轴分离要防的重排。

## 2. 规范轴：先跳过机器已强制的

`scripts/check-*.mjs`、eslint、`tsc`、覆盖率门禁已经覆盖的，**本清单不重复**——
重复会推高它的层级，并造成两处维护（正是 §15 元规则要防的）。

## 3. 规范轴：坏味道基线

机器查不到的部分，用 Fowler《重构》第 3 章的坏味道清单过一遍。
**每条都是判断，不是硬违规**：报告时写「可能的 X」并引用对应 hunk，不要写成门禁失败。

| 坏味道 | 是什么 → 怎么改 |
|---|---|
| 神秘命名 | 名字没揭示它做什么 / 存什么 → 重命名；起不出诚实的名字，说明设计本身含糊 |
| 重复代码 | 同一逻辑形状出现在多个 hunk / 文件 → 提取共享形状，两处都调它 |
| 依恋情结 | 方法访问别的对象的数据多于自己的 → 把方法搬到它依恋的数据上 |
| 数据泥团 | 同几个字段 / 参数总是结伴出现 → 并成一个类型再传 |
| 基本类型偏执 | 用 string / number 顶替一个领域概念 → 给这个概念一个小类型 |
| 重复的 switch | 同一类型的 switch / if 级联在改动里反复出现 → 换多态，或两处共享一张表 |
| 霰弹式修改 | 一处逻辑改动迫使修改散落在多个文件 → 把一起变的东西聚到一个模块 |
| 发散式变化 | 一个文件因几个不相关的原因被改 → 拆开，让每个模块只因一个原因变化 |
| 夸夸其谈通用性 | 为需求里没有的场景加抽象 / 参数 / 钩子 → 删掉；真需求出现前先内联回去 |
| 消息链 | 长长的 `a.b().c().d()` 导航 → 用第一个对象上的一个方法藏起这段遍历 |
| 中间人 | 类 / 函数大部分只是在转调 → 砍掉，直接调真正目标 |
| 被拒绝的遗赠 | 子类忽略或覆盖了它继承的大部分 → 放弃继承，改用组合 |

**本仓已文档化的规范优先于这份基线**：规范认可、而基线会报的，抑制掉。

## 4. 规格轴

对每个发现**引用规格里的原句**，分三类：

- 规格要求、diff 里**缺失或只做了一半**的；
- diff 里**没被要求**的行为（范围蔓延）；
- 看起来实现了、但**实现方式不对**的。

规格找不到时，**明说「无规格可比」并跳过这一轴**，不要替它编一个规格出来。

两轴都**只报，不改**：审查的产出是发现，不是就地修复。
